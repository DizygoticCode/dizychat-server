# Android Slice 2 Push Architecture

Date: 2026-09-05
Base: `main` at `1bb08b03ba52015fe4862a812785b4143f270c30`

## Goal

Add reliable Android push notifications to DizyChat while keeping DizyChat itself authoritative for identity, room membership, read state, notification eligibility, reply authorization, and message storage.

Firebase Cloud Messaging (FCM) is transport only. FCM must not become the authority for room membership, subscriptions, authentication, read state, or message actions.

Slice 2 covers:

- push delivery for messages in rooms joined by that Android device;
- notification tap routing to the correct room and exact message;
- inline notification Reply using DizyChat's existing reply semantics;
- Mark as read using account-wide per-room read state;
- one continuously updated Android notification per room;
- correct behaviour for foreground, background, locked-screen, multiple-device, logout, revocation, and browser-read cases.

## Existing foundations

The design reuses the existing durable Android mobile session rather than adding a second authentication mechanism. The existing `MobileSession` remains the authority that ties an Android installation to an authenticated account.

The existing message model already supports `replyTo` and `replyToSnapshot`; notification Reply must create the same kind of ordinary DizyChat message as an in-app reply.

The existing global `Message.status` field must not be reused as per-user read state because one participant reading a group-chat message does not mean every participant has read it.

The repository already includes `@capacitor/push-notifications`; Android delivery will use FCM through that integration.

## Chosen transport

Use direct per-device FCM delivery controlled by the DizyChat server.

Rejected alternatives:

1. FCM topics per room. Rejected because Firebase would gain too much responsibility for room subscription state and per-device suppression becomes harder to reason about.
2. Keeping a socket alive and generating only local notifications. Rejected because Android may suspend or kill the app; reliable screen-off/background delivery is a core requirement.

FCM receives only the payload required to deliver a notification. It never decides who is eligible to receive one.

## FCM server implementation boundary

Use the Firebase Admin SDK on the self-hosted DizyChat server for FCM HTTP v1 delivery rather than hand-rolling Google OAuth/service-account signing.

Use a dedicated Firebase service account restricted to the minimum project role needed for FCM sending. Its credential file remains outside the repository and outside the APK, readable only by the DizyChat service account on the host. The server receives the credential location through secret deployment configuration such as `GOOGLE_APPLICATION_CREDENTIALS` or an equivalent DizyChat-specific path variable.

Do not commit a service-account JSON file, embed it in JavaScript, add it to the Android assets, or expose it to GitHub Actions unless a later CI design explicitly requires a separate test credential. Normal deterministic CI must use a fake push transport and require no live Firebase secret.

## Notification eligibility

When a normal room message has been accepted and stored, DizyChat evaluates Android devices independently.

A device is eligible only when all of the following are true:

- its mobile session is valid and not revoked;
- its push registration is active;
- that device is subscribed to the message room;
- the sender is not the same account as the device owner;
- the device does not currently hold a valid `foreground + screen interactive` suppression lease;
- the message is newer than the account-wide read cursor for that room.

Browser activity never suppresses phone push delivery merely because the same account is open in a browser.

If the phone screen is off or locked, push remains eligible even when the app had previously been foregrounded. This is required so Android can produce the expected notification sound/vibration while the phone is locked.

If device visibility state is uncertain or stale, DizyChat errs toward sending the notification rather than silently dropping it.

## Device model

Create a dedicated push-device record rather than expanding `MobileSession` into a notification catch-all.

Each record represents one Android installation/mobile session and stores at minimum:

- stable device identifier generated by the app;
- associated mobile-session identity/reference sufficient to prove account ownership;
- canonical username/account identifier;
- current FCM registration token;
- device label/platform metadata as useful for operations;
- token registration/update timestamp;
- disabled/retired timestamp or state when appropriate;
- last valid foreground/screen-interactive lease expiry;
- created/updated timestamps.

The FCM token is not an authentication credential. Every state-changing DizyChat operation still requires the normal mobile session.

A single account may have multiple active Android device records. Each device is evaluated independently.

When FCM reports a token as permanently invalid/unregistered, retire only that token/device push registration. Temporary FCM failures must not delete device state, room subscriptions, mobile sessions, or account state.

## Per-device room subscriptions

Room notification subscriptions are per Android device, not account-wide.

Joining a room on an Android device adds the device+room subscription.
Leaving that room on that Android device removes the subscription.

Two phones on the same account may therefore be subscribed to different rooms.

Leaving a room must stop future pushes for that room on that device without requiring logout.

Logout or mobile-session revocation must make that device immediately ineligible for authenticated push actions and future notification delivery.

The server remains authoritative for validating that a subscription corresponds to a room the authenticated account is permitted to join.

## Account-wide read cursor

Create a separate account+room read-cursor record.

The cursor stores the latest message read by that account in that room. Ordering is the tuple `(message.timestamp, message._id)` in ascending order. Cursor advancement is compare-and-set/monotonic: an older or equal tuple can never move the cursor backwards or create a second advancement.

The cursor stores both the target message identifier and its timestamp so the ordering decision is deterministic and does not depend on client clocks.

The cursor is account-wide rather than device-local.

It advances when the account actually reads messages through any supported client, including:

- Android chat view;
- browser chat view;
- notification `Mark as read` action.

Merely having the browser open does not advance the cursor.

When the cursor advances, live sessions for that account receive a read-state update. Android devices belonging to that account clear or update any room notification that no longer represents unread messages.

This means:

- browser open, unread message: phone notification still arrives;
- browser actually reads message: shared read cursor advances and the phone's stale unread notification is cleared;
- one Android device marks the room read: other Android devices for the same account clear/update that room notification as well.

## Foreground and screen-state suppression

Do not store a permanent boolean such as `foreground=true` because it can become stuck when Android kills the app.

Use a short-lived suppression lease representing:

`app foreground AND screen interactive`

The Android client refreshes this lease only while both conditions remain true.

The lease is cleared immediately when either condition becomes false where lifecycle delivery permits. If the app disappears without clearing it, natural lease expiry restores push eligibility.

Screen interactivity must come from native Android state using `PowerManager.isInteractive()` combined with activity/application lifecycle state. JavaScript/WebView visibility alone is insufficient.

Required behaviour:

- app foreground + screen on/interactive: suppress system push;
- app background + screen on: push eligible;
- app foreground but screen off/locked: push eligible;
- app killed/swiped away: push eligible;
- stale/missing lease: push eligible.

Each Android device has its own lease. Activity on a browser or another Android device must not suppress this device.

The implementation plan must choose an explicit lease duration and heartbeat interval with the constraint that lease duration exceeds at least two heartbeat intervals, so one missed heartbeat does not immediately create duplicate notifications while process death still recovers promptly.

## Notification permission

On Android versions requiring runtime notification permission, request it after the user successfully joins their first room, not immediately on app launch or login.

The prompt should therefore have clear context: notifications are for rooms the user joins.

Declining permission must not break chat, authentication, room membership, or Socket.IO delivery. Device registration remains inactive for system notifications until permission is later granted.

## Notification content and grouping

Use one Android notification per room, updated as newer unread messages arrive.

The displayed content includes:

- sender;
- room;
- a short, safe text preview when available.

For attachment-only messages use a human-readable description such as:

- `sent an image`;
- `sent a voice message`;
- `sent a video`;
- `sent a file`.

Do not expose raw upload URLs when a human label is sufficient.

Use Android's messaging-style notification presentation for the recent unread messages represented by that room notification. If the device/OS cannot retain the full recent stack, correctness falls back to showing the latest unread sender/preview while preserving the same stable room notification identity.

Multiple unread messages in the same room update the existing room notification rather than producing one notification per message.

The notification's current action target is the latest unread message represented by that notification.

## Notification payload security

The push payload may contain routing/display identifiers such as:

- room identifier/name;
- message identifier;
- sender display name;
- safe preview/action metadata;
- notification grouping identifier.

It must never contain:

- mobile-session token;
- browser-session token;
- MongoDB credentials;
- Firebase service credentials;
- room password;
- server secrets;
- signing secrets;
- any other credential that would let possession of the notification authorize an operation.

Push payloads are hints for routing and display only. Every mutation is re-authorized by DizyChat.

## Tap routing

Tapping the room notification must:

1. launch or resume DizyChat;
2. restore the existing secure Android mobile session;
3. validate that session with the DizyChat server;
4. verify current room access;
5. enter the target room;
6. locate and scroll to the exact target `messageId`.

If the session is missing/revoked or room access has been lost, do not bypass normal authentication or room authorization. Route the user through the normal login/access flow instead.

A notification tap does not itself constitute authorization.

## Inline Reply

Inline notification Reply must behave exactly like replying inside DizyChat.

Flow:

1. Android captures reply text from the notification action.
2. The app sends an authenticated request to DizyChat using the existing secure mobile session.
3. The server validates the mobile session.
4. The server validates current room access.
5. The server validates the target message belongs to that room and remains a valid reply target under existing chat semantics.
6. The server creates a normal DizyChat message using the existing `replyTo` and reply snapshot behaviour.
7. The message follows the ordinary message-storage and Socket.IO publication path.

No separate push-only message type is introduced.

If authentication or authorization fails, no chat mutation occurs.

## Mark as read

`Mark as read` means `mark this account's room read through this notification's target message`; it is not merely a local notification dismissal.

Flow:

1. Android sends an authenticated request using the secure mobile session.
2. The server validates account identity and room access.
3. The server advances the account+room read cursor monotonically through the target message.
4. The server emits/synchronizes read-state changes to live clients for that account.
5. Android notifications for that account+room are cleared or updated across the account's registered Android devices.

If authorization fails, the server does not mutate read state.

## FCM service boundary

Implement FCM behind a small server-side push transport interface so recipient-selection policy and FCM mechanics remain independently testable.

The policy layer decides recipients and constructs an approved notification intent.
The transport layer performs direct token delivery through Firebase Admin SDK.

The server must run normally with push transport disabled/unconfigured.

Message persistence and Socket.IO publication must never wait for or depend on successful FCM delivery.

Push sending is best-effort/asynchronous after the message has been accepted. FCM failure may be logged and retried according to a bounded retry policy chosen in the implementation plan, but must not cause a chat message to fail or be duplicated.

## Read-state clearing of existing notifications

The account+room read cursor is authoritative.

Whenever it advances, the server sends an idempotent FCM data/control message to every active Android push registration for that account telling the device to reconcile that room through the new cursor. A connected Socket.IO session may mirror the same event for lower latency, but correctness must not depend on the socket being alive.

The device compares the control message's cursor against the latest message represented by its stable room notification and clears or updates only that room notification as appropriate.

Startup/reconnect reconciliation also fetches or receives the current server read cursor and removes stale notifications whose represented latest message is already at or behind it.

Contracts:

- account read cursor is authoritative;
- control messages are idempotent;
- out-of-order older control messages cannot roll back state;
- clearing one room does not clear unrelated rooms;
- clearing a notification never fabricates or advances read state on its own.

## Stable per-room notification identity

Each Android installation derives a stable notification identifier from its stable device/account namespace plus room identifier, using a deterministic collision-resistant mapping suitable for Android integer notification IDs. The implementation plan must define the exact mapping and collision handling.

The identity remains stable across app process restarts.

Clearing one room notification must not clear unrelated rooms.

## Error handling

### Permanent FCM token failure

Retire that token registration and require a later client token registration/rotation before future delivery.

### Temporary FCM/network failure

Keep session, device, subscription, and read state unchanged. Chat message remains stored and published normally.

### Revoked/expired mobile session during action

Reject Reply/Mark-as-read. Do not mutate chat/read state. Require normal reauthentication.

### Lost room access

Reject Reply/Mark-as-read and do not route directly into a room the account may no longer access.

### App killed before clearing foreground lease

Lease expiry restores push eligibility automatically.

### Notification permission denied

No system notification is delivered, but all ordinary DizyChat functionality continues.

Add:

- Mark as read through account+room read cursor;
- FCM read-control messages plus startup/reconnect notification reconciliation;
- cross-device/browser-read notification clearing;
- permanent invalid-token retirement;
- full end-to-end regression coverage.

## Non-goals

This slice does not:

- migrate DizyChat messaging/auth/room state into Firebase;
- use FCM topics as the room authority;
- add iOS push notifications;
- fix the separate iPhone/Safari voice-message codec/container compatibility issue;
- change normal browser relative-media behaviour;
- alter the existing Android Slice 1 authentication contract except where push registration consumes that authenticated identity;
- introduce Google Play distribution.

## Security summary

The self-hosted DizyChat server remains authoritative.

FCM is a courier only.

A notification can request an action, but it cannot authorize one.

Every Reply, Mark-as-read, room subscription mutation, and tap destination is validated against the current authenticated DizyChat account/session and room access at execution time.

Credentials stay outside Git, outside notification payloads, and outside the APK wherever they are server credentials.

If FCM fails, DizyChat chat continues to work.
